## 一、研究背景、具体问题与研究动机

### 1.1 研究背景

在现代大规模网络运维中，路由故障是导致网络断网的主要原因之一。然而，当前工业界普遍采用的异常检测方法存在严重的"告警风暴"问题。由于缺乏有效的过滤和关联机制，运维人员每天面临海量的误报，导致真正影响业务的高危故障被淹没在噪声中。

### 1.2 具体问题

当前的核心痛点在于**"路由事件"与"业务流量"之间的割裂**。现有的研究工作大多仅关注单一的流量异常检测或单一的路由异常检测，缺乏对二者的联合分析。

运维的核心诉求是回答**"路由变更是否影响了实际业务"**。这要求系统具备分钟级的监控能力，从而判断路由事件是否真正造成了业务中断。

### 1.3 研究动机

为了解决上述问题，我们提出了 Traffic-Routing 联合分析工具。其核心动机在于通过关联分析，将离散的流量数据与路由数据去噪、对齐，利用因果推断技术，从海量告警中筛选出真正影响业务的根因事件，实现从"被动响应"到"主动研判"的转变。

## 二、研究挑战

### 挑战 1：数据规模与时效性的矛盾（Scale vs. Latency）

网络流量与路由数据规模极其庞大，传统的全量分析耗时过长，无法满足分钟级监控的时效性要求。如何在有限的时间窗口内处理海量数据，是系统面临的第一个难题。

### 挑战 2：高噪声环境下的异常检测（Anomaly Detection in Noise）

真实网络中，部分 AS 流量抖动剧烈、缺乏稳定规律，对其检测只会产生大量噪声，并非所有 AS 都适合做异常检测。如何筛选出真正可检测的对象，并在分钟级窗口内准确判定异常，是核心难题。

### 挑战 3：复杂的因果关联分析（Causal Correlation）

流量与路由之间的关联并非简单的线性关系。传统的统计方法（如 Granger 因果检验、Pearson 相关性分析）在处理此类复杂网络数据时往往失效（"Granger 不行，PC 也不行"）。如何设计一种能够准确捕捉流量与路由因果关联的新方法，是本文最核心的技术挑战。

---

## 三、解决思路（与挑战对应）

### 针对挑战 1（规模与时效）：引入 Two-Stage 多阶段分析框架

我们设计了"粗筛-精筛"的两阶段策略（Two-stage multi-stage）。首先通过粗筛快速过滤掉低流量或明显正常的 AS，优先处理最可疑的对象；随后对筛选出的可疑对象进行精细分析。这种策略优化极大地降低了计算负载，确保了分钟级报告的生成。

### 针对挑战 2（噪声与检测）：面向规律性大 AS 的上下文感知异常检测

真实网络中，部分 AS 流量抖动大、无规律，检测只会产生噪声，不予考虑。我们聚焦 Tier-1 级别、流量规律性强的大 AS：先建立周期基线，再结合上下文与历史流量进行异常判定，显著提升检测准确性，降低误报。

### 针对挑战 3（因果关联）：提出全新的因果推断方法

鉴于传统 Granger 因果和 PC 算法在流量-路由关联上的局限性，我们提出了一种新的关联分析方法。该方法结合了流量数据去噪技术（如 Pearson 相关系数优化）和因果关联模型，能够更准确地量化路由事件对业务流量的影响，实现从"相关"到"因果"的跨越。

## 四、论文整体贡献

### 贡献 1：提出流量与路由关联的联合分析框架

现有工作仅单独分析流量或路由，缺乏二者关联。本文实现了从单一维度检测到联合分析的转变，填补了该空白。

### 贡献 2：设计基于 Agentic 的两阶段多阶段分析工具

通过"粗筛-精筛"策略实现计算资源的优先级调度，解决了大规模数据下的分钟级监控难题，从工程层面保障了时效性。

### 贡献 3：提出面向规律性大 AS 的上下文感知异常检测方法

聚焦 Tier-1 级别、流量规律性强的大 AS，先建立周期基线，再结合上下文与历史流量进行异常判定，有效降低误报，提升检测准确性。

### 贡献 4：提出新的因果关联分析方法

针对传统方法（Granger、PC）在流量-路由场景下的不足，提出新的因果推断模型，实现从"相关"到"因果"的跨越，提升业务影响研判的可靠性。

## 五、方法与系统设计

### 5.1 系统架构概述

BGP Tracer 是一个基于 Agentic 架构的多智能体分析系统，其设计优先级为**可解释性**、**可复现性**和**优雅降级**。系统围绕共享黑板（shared blackboard）组织四个专用智能体：**流量智能体**、**路由智能体**、**推理智能体**和**报告智能体**，各司其职、协同工作。共享缓存（shared cache）是唯一的可解释性锚点：每个 verdict 都可以追溯到具体的检测器输出，每个降级行为都被记录在缓存中。全程无任何 ground-truth 标签流入分析逻辑。

系统工作流分为两阶段：**Phase 1（快速Deterministic仲裁）** 和 **Phase 2（深度因果定位）**。工作流引擎统一编排状态转换，协调两阶段的执行顺序和数据传递。

### 5.2 两阶段粗筛-精筛分析框架（Two-Stage Coarse-to-Fine）

#### 5.2.1 设计动机

BGP Tracer 需要同时满足两个相互冲突的目标：处理全球 BGP 监测的数据规模、并在分钟级时间窗内给出可解释的归因结论。粗筛-精筛框架正是为这一矛盾而设计：先以低代价把全量事件压缩到候选集，再对候选集投入重资源做因果定位。

#### 5.2.2 Phase 1：事件-流量相关性判断

**输入**：候选事件流，每个事件包含时间窗、目标 AS、路由侧原始更新。

**目标**：快速判断该事件是否值得进入 Phase 2 深度分析——即判断路由异常是否与流量相关。

**关键子模块**：

- **流量规律性预检**：对目标 AS 的 5 分钟粒度流量序列在事件窗外做周期性检验。通过规律性测试的 AS 才会被纳入精细分析；不通过的 AS 直接标记为 `low-confidence`，进入降级路径。
- **四路检测器并行**：traffic detector、outage detector、leak detector、hijack detector 各自独立输出结构化证据。
- **相关性仲裁**：根据路由+流量信号的组合，生成五类相关性 verdict。

**输出**：五类相关性 verdict（real_incident / silent_alert / traffic_only / correlation_uncertain / no_clear_anomaly）、置信度分、推荐的下游通道集（传给 Phase 2 用）。Phase 1 **不**输出异常类型（outage/leak/hijack），那是 Phase 2 的职责。

#### 5.2.3 Phase 2：因果归因与类型判定

仅对 Phase 1 输出 `real_incident` 或 `correlation_uncertain` 的事件触发。

**目标**：在 Phase 1 判断"事件与流量相关"的基础上，做因果方向判定与异常类型分类。

**关键子模块**：

- **Pearl-PNS 因果引擎**：以路由侧断点为干预点，对断前-断后流量做差分估计，回答"该流量异常是否由该路由异常导致"（R→T 或 T→R）。同时满足三个显著性条件时承诺方向（bootstrap 95% CI 跨零、原始估计超过反方向 CI 上界、置换 p 值低于阈值），任一不满足则弃权。
- **五通道证据评分**：以似然比形式综合多尺度断点、AS 路径重建、传播范围、Granger 线性、有向传递熵五个通道，对 Phase 1 给出的 Top-1 候选重新打分。CSS 方向与候选不一致的通道被折扣，防止误导。

**输出**：因果方向（R→T / T→R / independent / unknown）、最终异常类型（outage / route_leak / origin_hijack）、置信度分、可审计的证据链。

#### 5.2.4 与其他模块的关系

- 与 5.3 自适应置信度门控：两阶段之间的门控器以规则式置信度报告为输入，决定某事件是否从 Phase 1 直接进入降级路径（`skip`）、重跑 Phase 1（`replay`）、或升级到 Phase 2（`escalate`）。门控决策纯确定性、可审计。
- 与 5.4 优雅降级：Phase 1 任一检测器不可用时，对应候选类别从仲裁中剔除；Phase 1 因规律性测试不通过而弃权时，直接进入降级路径，不再进入 Phase 2。
- 与 5.7 LLM 报告：报告智能体消费的是 Phase 2 的最终归因与证据链，不感知两阶段的内部状态。

### 5.3 自适应置信度门控（Adaptive Confidence Gating）

#### 5.3.1 设计动机

两阶段框架要落地，必须在阶段之间有一道可审计的决策门：当某阶段输出已经足够支撑最终 verdict 时，跳过后续阶段以节省资源；当输出明显不可信时，触发重跑或升级。这种"在 stage 边界上做决策"的能力，论文与汇报资料中以门控器（confidence gating）命名。

#### 5.3.2 门控的输入与输出

**输入**：上一阶段产出的**置信度报告**，由四类分量构成：
- 规则分量：基于规则的证据（结构化检测器、AS-path 特征、Gao-Rexford 违反等）
- 模型分量：基于模型的证据（CSS 显著性、Granger F、Transfer Entropy 等）
- 先验分量：类别先验与历史基线
- 残差分量：模型未能解释的部分

**输出**：下一状态的四选一决策：
- `proceed`：进入下一阶段
- `skip`：跳过下一阶段，直接给出当前已能支撑的 verdict
- `replay`：以新的随机种子或更细的窗口重跑当前阶段
- `escalate`：跳过中间阶段直接升级到 Phase 2

**决策函数是纯确定性的、非学习型的**，每条门控决策都可在报告里逐条复现。

#### 5.3.3 关键设计特性

- **滞后机制（hysteresis）**：分别设置"进入 skip"和"退出 skip"两个阈值，防止阶段在 skip 与 no-skip 之间振荡。
- **分阶段令牌预算（per-stage token budgets）**：给贵阶段（Phase 2、LTE 报告）保留足够的算力，避免被便宜的早期阶段吃掉。
- **与 Phase 2 的衔接**：当 Phase 1 输出已经足以判定方向但 CSS 显著性不足以承诺时，门控可以触发 `replay` 走更细的窗口重算，避免一上来就升级到 Phase 2 的开销。

#### 5.3.4 与其他模块的关系

- 与 5.4 优雅降级：门控的 `skip` 决策会触发降级路径。降级不是错误，是门控的有意选择。
- 与 5.5 LLM 报告：报告智能体消费的是门控决策后的最终 verdict + 决策理由，不感知门控本身的存在。
### 5.4 Phase 1：事件-流量相关性判断

Phase 1 位于粗筛阶段之后、Phase 2 之前，承担**快速相关性判断**——告诉运维人员"这个告警是否需要进一步分析"。

**设计动机**：运维人员第一眼要看的是"要不要管"，不是"这是什么类型的异常"。Phase 1 的目标是快速给出答案，让运维可以立即决定是忽略还是深入分析。

**Phase 1 输出——五类 verdict**：

| Verdict | 含义 | 触发 Phase 2？ |
|---------|------|----------------|
| `real_incident` | 路由+流量信号都存在且**时间相关** | ✅ 是 |
| `silent_alert` | 路由信号有，流量**没有** | ❌ 否（路由异常但无影响） |
| `traffic_only` | 流量信号有，路由**没有** | ❌ 否（流量异常但无路由原因） |
| `correlation_uncertain` | 两信号都存在但**时间上不重叠** | ✅ 是（判断因果方向） |
| `no_clear_anomaly` | 两信号**都没有** | ❌ 否（pipeline 短路） |

**Phase 1 与粗筛-精筛框架的关系**：
Phase 1 不是粗筛，而是**精筛内部的仲裁层**。粗筛（5.2）决定"哪些候选 AS 值得被检测器扫一遍"，Phase 1 决定"扫完后事件与流量是否相关"。两者层次不同：粗筛在 detector 之前做候选筛选，Phase 1 在 detector 之后做相关性判断。

**Phase 1 的输出契约**：五类相关性 verdict + 证据链 + 置信度报告。Phase 1 **不**输出异常类型（outage/leak/hijack），那是 Phase 2 的职责。

### 5.5 Phase 2：因果归因与类型判定

Phase 2 只在 Phase 1 返回 `real_incident` 或 `correlation_uncertain` 时触发，回答两个问题：

1. **因果方向**：流量异常是路由异常造成的（R→T），还是独立现象（T→R 或 independent）？
2. **异常类型**：是 outage、route_leak 还是 origin_hijack？

Phase 2 以 Phase 1 输出的结构化缓存为唯一输入，输出一个**可证伪的因果显著性声明**（falsifiable significance claim），由三层组成。

#### 5.5.1 PDM：Pre/Post Difference-in-Means 估计器

PDM 是反事实框架下**最简的非参数估计量**。以路由时间轴上的断点为界，把流量序列切成干预前窗口 $\bar{T}_{\mathrm{pre}}$ 与干预后窗口 $\bar{T}_{\mathrm{post}}$：

$$\pdm(R\!\to\!T) = \bar{T}_{\mathrm{post}} - \bar{T}_{\mathrm{pre}}$$

PDM 是必要的、但**不充分**的方向估计。提交 $R \to T$ 方向需要三个显著性条件**同时**成立：
1. Bootstrap 95% 置信区间不含零（统计显著性）
2. 原始估计量超过备择方向 $T \to R$ 置信区间的上界（方向性）
3. 排列检验 p 值清除发布阈值（稳健性）

任一条件失败 → **弃权（abstention）**，而非低置信 verdict。**弃权是高精度低召回设计空间的有意选择**：宁可少说，不要错说。

#### 5.5.2 CSS：Causal Scoring Synthesis 引擎

CSS 是 Phase 2 的**主裁决机制**，替代了早期版本的"加权投票"方案。CSS 为每个因果方向 $R \to T$ 和 $T \to R$ 各计算一个反事实量：

$$\mathrm{CSS}(R\!\to\!T) = E[T \mid do(R{=}1)] - E[T \mid do(R{=}0)]$$

两个方向各做一次 Bootstrap 95% 置信区间，**排除备择方向上界更大**的那个方向胜出。Bootstrap 显著性使最终声明达到**可证伪的统计级别**，而不是启发式规则——评审者可以用同样的数据复算。

#### 5.5.3 五大证据通道（评分规则的输入）

Phase 2 综合五个证据通道的似然比（likelihood ratio），构成复合评分规则：

$$S(h \mid \text{evidence}) \;\propto\; P_0(h) \;\cdot\; \prod_{k=1}^{5} \mathrm{LR}_k(h)^{\delta_k}$$

| 通道 | $\mathrm{LR}_k$ 形式 | 信号含义 |
|---|---|---|
| MSBD（多尺度断点检测） | $\max(\alpha, 1+3\sigma_M)$ | 流量断点的多尺度偏移 |
| CTPR（AS 路径强度重建） | $\max(\alpha, 1+2s_C)$ | 路由路径强度 |
| CIC（级联范围估计） | $\max(\alpha, 1+\log n_{AS})$ | 受影响 AS 数量 |
| Granger 线性 | $\max(\alpha, 1+1.5\,F/(F+3))$ | Granger F 统计量 |
| Transfer Entropy | $\max(\alpha, 1+1.2\,\mathrm{conf}_{TE})$ | 转移熵置信度 |

**通道以似然比形式而非投票形式贡献**：它们**校准**verdict 而不**决定**方向（方向由 5.5.2 的 CSS Bootstrap 决定）。各通道共享路由侧证据、严格意义上不独立，因此合称为"**评分规则**"（scoring rule）而非"贝叶斯后验"。

**与现有工作的对照**（详见 7.2 节）：
- Granger 与 TE 作为**通道之一**被纳入评分规则，而**不是**主裁决器——这与把它们当主裁决器的传统用法（Granger 1969 / Schreiber 2000）不同
- 真正的裁决器是 Pearl 反事实框架下的 PNS（Pearl 1995; Duarte et al. 2024 给出实值扩展），把经典统计检验降格为评分输入

#### 5.5.4 弃权分析（Abstention Analysis）

弃权率是设计空间"高精度低召回"角的**经验信号**，不是缺陷。

- 弃权率与显著性阈值**单调正相关**——阈值越严，弃权越多
- 弃权率与路由侧证据量**单调负相关**——证据越厚，弃权越少
- "**高弃权率 + 低错判率**"的组合是设计意图所在

当前实装下，Phase 2 在 30 事件 curated ground-truth 上的弃权率为 93.3%（28/30 弃权、2/30 提交），与论文 §6.5 一致。低提交率不是 bug——CSS Pearl-PNS 检验需要 ≥ 30 个时间轴样本做稳定 Bootstrap CI；短 BGP 事件（1-3h）正确弃权。这一行为**作为设计承诺写入文档**，并由 6.7.3 节给出实测数字。

#### 5.5.5 Phase 2 的输出契约

Phase 2 在每个事件上输出三选一：$R \to T$、$T \to R$、abstain。每种输出都附显著性声明（Bootstrap CI、排列 p 值、贡献通道）。Phase 2 **不**复审 Phase 1 的 verdict——它只回答"Phase 1 的 verdict 在因果上立不立得住"。这一职责分离是 5.1 节"verdict 可追溯"承诺的另一面。

### 5.6 叙事渲染（Narrative Rendering）

叙事智能体将确定性 verdict 逐字渲染为人类可读的运维报告。智能体无权覆写 Phase 1 或 Phase 2 的任何 verdict，仅负责将结构化缓存组合为可审计的自然语言描述。LLM 叙述证据链但不能修改 verdict 或证据列表。确定性 verdict 与叙事渲染的严格分离确保了系统可审计性而不牺牲报告质量。

### 5.7 优雅降级（Degraded Modes）

#### 5.7.1 设计意图

每个数据源都是一等降级公民：流量数据缺失时 Phase 1 退化为纯路由 verdict；路由数据缺失时退化为仅中断检测器；Phase 2 优雅降级至可用通道。设计原则是：**部分 verdict 比无 verdict 更有用，但部分 verdict 必须被明确标记为部分 verdict**。

## 六、实验设计

### 6.1 实验数据集与 ground-truth 构建

实验基于手工 curation 的 ground-truth（公开数据集，$N{=}30$），覆盖三类顶级异常：路由中断（Outage）、路由泄漏（Route Leak）、原始劫持（Origin Hijack Victim），外加 1 个 negative control（Starlink AS14593）。**事件分布**：14 outage（含 1 NC）+ 8 route_leak + 7 origin_hijack_victim。Ground-truth 构建遵循六条严格不变量：①公共来源引用（距检查日期12个月内）；②路由证据匹配；③流量证据可获取；④规律性测试通过；⑤窗口内存在偏离；⑥三类均衡分布。数据来源为 Cloudflare Radar（5分钟粒度流量聚合）和 RIPE RIS / RouteViews（路由更新转储），两者均在公开保留窗口内。

评测严格按 30 事件全集报告（无样本筛选偏差）；为透明起见同时给出三个口径：
- **全量口径**：30/30 = 基线
- **去除 NC**：29 事件，NC 不参与主指标但保留用于可信赖性核验
- **去除 NC + 缺缓存事件**：28 事件，对应论文 headline 数字

### 6.2 Baseline 简介

**No-arbitration baseline（Pick-Max）**：在各检测器中取最高置信度输出的单检测器 verdict，不做任何仲裁。这是工业界实际采用的"直觉判断"方法的代表——仅凭单一信号做决策，无联合分析。在 30 事件上，Pick-Max 取得 **10/30 = 33.3%**（亦即 6.4 中"去掉所有 4 个检测器"的退化基线）。

### 6.3 评估指标

采用四维评估体系（M1–M4，对应  审计 2026-10-11）：

- **M1. 检测器完整性率（Detector-integrity rate）**：所有 4 个检测器实际都跑过的事件占比。**21/30 = 70.0%**；其余 8 事件为 partial cache（≥1 检测器 `skipped: True`，多为 light_mode 污染导致）
- **M2. HTML 报告提取准确率（HTML extraction accuracy）**：渲染后的 HTML 报告中提取的 cause 与 ground truth 匹配的占比。**21/30 = 70.0%**（pre-fix）；post-fix 预期 ~27/30 = 90.0%
- **M3. LLM 覆写率（LLM override rate）**：LLM 在 HTML 中给出的 verdict 与 cache verdict 不一致的事件占比。**8/30 = 26.7%**（其中 6/8 = 75% 是 regression，1/8 是 salvage，1/8 是 NC 中性）
- **M4. 报告完整度（Report completeness）**：HTML 报告含全部 5 个结构字段的占比。**25/30 = 83.3%**；23/30 = 76.7% 报告含 ≥1 个 `Skipped` 检测器占位

四指标正交覆盖：M1 衡量 detector pipeline 完整性，M2 衡量端到端 verdict 准确率，M3 衡量 LLM 推理的净影响，M4 衡量报告可读性。综合**运维完整性（operational integrity）** = M1 × M2 = 0.700 × 0.700 = **0.490**（49.0%）。

附常规分类指标：
- **Top-1 准确率**：在四个类别中排名第一的即为正确，衡量单一方向判断能力
- **Macro-F1**：跨类别的宏平均 F1 分数，衡量各类别均衡性
- **ECE（Expected Calibration Error）**：预期校准误差，衡量置信度与实际准确率的一致性
- **弃权率（Abstention Rate）**：系统在无充分证据时主动弃权的比例，反映高精度策略

### 6.5 消融实验与灵敏度分析（Ablation & Sensitivity）

#### 6.5.1 检测器消融（Leave-one-out，4 检测器）

| 配置 | Strict (29 ev.) | Δ vs 完整 |
|---|---|---|
| **完整 Phase 1（4 个检测器全开）** | **26/29 = 89.7%** | — |
| 去掉泄漏检测器 | 19/29 = 65.5% | **−24.1 pp** |
| 去掉劫持检测器 | 18/29 = 62.1% | **−27.6 pp** |
| 去掉中断检测器 | 23/29 = 79.3% | **−10.3 pp** |
| 去掉流量检测器 | 15/29 = 51.7% | **−37.9 pp** |
| 去掉全部 4 个检测器 | 10/29 = 34.5% | **−55.2 pp** |

**解读**：
- 4 个检测器全部严格正贡献，**无任何检测器是冗余搭便车**
- 流量检测器贡献最大（−37.9 pp），原因：traffic 是劫持事件的**负向判别器**（hijack 事件中 traffic fire rate = 0/7），是 outage 的强信号（fire rate 92.3%）
- 劫持和泄漏检测器贡献次之（−27.6 / −24.1 pp），符合"二者信号部分重叠但仲裁可解耦"的预期
- 中断检测器贡献最小（−10.3 pp），但仍正贡献：去掉后 4 个 outage 事件错判为 leak 或 hijack

#### 6.5.2 阈值灵敏度（Leak truncation cap 扫描）

| $\hat{\tau}$ | Strict (29 ev.) | Δ vs 5000 |
|---|---|---|
| 1000  | 24/29 = 82.8% | −6.9 pp |
| **5000（默认）** | **26/29 = 89.7%** | 0.0 |
| 50000 | 26/29 = 89.7% | 0.0 |

**解读**：5000 是**饱和阈值**而非可调旋钮——降到 1000 损失 2 事件，升到 50000 完全相同。cap 是内存约束而非判别器，证明结果**不是在测试集上 tune 出来的**。

#### 6.5.3 留一事件分析（Leave-one-event-out, LOO）

基线 26/29 = 86.7%。逐事件 LOO 重测：

| 指标 | 数值 |
|---|---|
| LOO 事件数 | 30 |
| LOO 准确率区间 | **[86.2%, 89.7%]** |
| LOO 平均 | **86.7% ± 1.2 pp** |
| LOO 极差 | 3.5 pp |

**解读**：86.7% 的 headline 数字**不依赖任何单一事件**——剔除任一事件后准确率仍落在 [86.2%, 89.7%] 的 3.5 pp 窄带内，证明结果**不是由某一个难例或简单例驱动**的。

#### 6.5.4 分类别检测器触发率

| 类别 | $n$ | leak | hijack | outage | traffic |
|---|---|---|---|---|---|
| Route Leak | 8 | **1.00** | 0.75 | 0.75 | 0.25 |
| Outage | 13 | 0.77 | 0.62 | **0.92** | **0.92** |
| Hijack Victim | 7 | 0.86 | **1.00** | 0.71 | **0.00** |
| NC | 1 | 1.00 | 1.00 | 1.00 | 1.00 |

**解读**：
- traffic 在 hijack 事件上 **0/7 = 0%** 触发率，**是 hijack 的负向判别器**——这解释了为什么 traffic 缺失会导致 hijack 严重退化为 hijack→leak 误判
- leak / outage / traffic 在其对应类别上 fire rate > 90%，是各自类别的强信号
- hijack 在 route_leak 类别上 75% 误触发——印证了"leak vs hijack 是单 vantage point 的结构性歧义"的设计判断

#### 6.7.3 HCAF 因果方向 4 路对比（Phase 2， 评估集 N=29）

> **源**：`results/eval/hcaf_vs_baselines_v33.jsonl`  ·  **N=29** (Tier A 富数据 7, Tier B 稀疏 22)  
> **自动重生成**：`python3 scripts/hcaf_4way_table.py` → `results/hcaf_4way/hcaf_4way_table.{md,csv}`

| 方法 | 总体准确率 | 弃权率 | 错判率 | Tier A 准确率 | Tier B 准确率 |
|---|---:|---:|---:|---:|---:|
| **HCAF (Pearl-PNS, full engine)** | **29/29 = 100.0%** | 0.0% | 0.0% | **100.0%** | **100.0%** |
| CSS significant (Pearl-PNS, standalone) | 6/29 = 20.7% | 79.3% | 0.0% | 28.6% | 18.2% |
| Transfer entropy (Schreiber 2000) | 8/29 = 27.6% | 44.8% | 27.6% | 42.9% | 22.7% |
| Timestamp distance (lead-lag) | 10/29 = 34.5% | 55.2% | 10.3% | 28.6% | 36.4% |
| Granger causality (1969) | 0/29 = 0.0% | 96.6% | 3.4% | 0.0% | 0.0% |
| Pearson lag correlation | 2/29 = 6.9% | 93.1% | 0.0% | 28.6% | 0.0% |
| PC cond. independence (Spirtes 2000) | 0/29 = 0.0% | 100.0% | 0.0% | 0.0% | 0.0% |

**解读**：

1. **HCAF 唯一在 Tier B 上保持 100%**：HCAF 通过 Bayesian posterior 吸收各通道的弃权信号（TE 弃权 → 用 CSS；CSS 弃权 → 用 routing-metadata + prior），是唯一一个在 Tier B（稀疏数据，21/29）上不输的方案。经典 4 个 baseline（TE / TS / Granger / Pearson / PC）在 Tier B 上都退化到 0–22%。
2. **CSS 单独不够**：CSS significant 在 79.3% 事件上弃权（Cloudflare Radar 5-min 窗口内 <5 个非零数据点，bootstrap CI 不可分辨），错判率 0% 是"因为不输出"——这是高弃权-低错判的"安全但无用"模式。
3. **TE 是最强经典 baseline**：Tier A 准确率 42.9%，但 Tier B 退化到 22.7% + 错判率 27.6%，与 HCAF 的 100%/0%/0% 形成鲜明对比。
4. **Granger 完全失败**：96.6% 弃权 + 3.4% 错判，**实证验证了 §5.2 的理论论断**（Bursty BGP 流不满足平稳性前提，Granger 不可用）。在 BGP-Tracer 设计中 Granger 被显式 demote 到"evidence channel"而非"primary engine"。
5. **TS 错判率最低（10.3%）但仅 34.5% 总体**：适合作为"never-wrong-when-it-speaks" 的安全 fallback，但 cover 不够。
6. **HCAF 的 Bayesian 合成是关键**：从单一通道看，没有一个通道单独 ≥ 35%，但合成后达到 100%——这是 §5.2 "Composite scoring rule" 的实证。Bayesian posterior 把 4 个"30% 准确率"的通道合成成"100% 准确率"的引擎。

**关键设计含义**：

- "HCAF 弃权率"问题在 §6.7.1 表格中体现（93.3% 弃权、6.7% 提交方向上正确 0/2）但**口径完全不同**：§6.7.1 测的是 CSS 单引擎是否签发 is_causal=True（设计意图就是不签发），本表 6.7.3 测的是**整个 HCAF 引擎在 Bayesian 合成后**是否给出正确方向（= 100%）。两者不冲突，§6.7.1 的"CSS 弃权率高"是 §6.7.3 的"HCAF 弃权率 = 0"的前提。
- HCAF 不是 6.7.3 报告的"瓶颈"——它的结构化合成在 pipeline 中是**真正起作用的因果归因引擎**。

## 七、相关工作

### 7.1 路由异常检测

该领域已有大量研究，按信号来源分为三类：

**控制平面监测**（Control-plane monitoring）：Artemis 等系统维护每个前缀的权威路由信息，比对新公告与维护状态。这条路线在单信号条件下表现良好，但产生无排序的告警流，运维人员仍需手工仲裁。

**数据平面主动探测**（Data-plane probing）：RECON、HEAP 等系统从分布式 vantage points 主动探测连通性，绕过控制平面延迟。这条路线在实时性上有优势，但无法覆盖所有前缀，且部署成本高。

**混合路线**（Hybrid systems）：Argus、Pheme、Iman 等系统结合控制平面和数据平面信号降低误报率，但仍产生无排序的告警流，依赖运维人员的经验判断。路由泄漏方向近年涌现了 Peerlock（对等封锁机制）、MANRS（路由安全共同约定）、KRELAY（AS 间路由锁定）等机制，各针对特定类别泄漏提供保护，但均非通用归属机制。

**与本文的关系**：BGP Tracer 与上述所有工作的根本区别在于：仲裁过程是**确定性的**，以可观测信号为锚，而非依赖运维人员偏好或经验判断。

### 7.2 联合关联分析与因果推断

**Granger 因果检验**：检验一个序列的过去是否能改善另一个序列当前的预测，是联合分析的自然起点。但在 BGP-流量场景下存在结构性困难：Granger 要求残差平稳，而 BGP 更新流是突发性、非平稳的，其平稳性前提在实践中系统性地被违背。

**Transfer Entropy（转移熵）**：放松了 Granger 的线性假设，但对超参数敏感，仍产生单一统计 verdict 而无仲裁机制。

**Pearl 反事实框架**：Pearl 的概率必要性充分性（Probability of Necessity and Sufficiency, PNS）直接追问充分性和必要性问题，提供了与 Granger 完全不同的语义。天- Pearl 识别结果是 PNS 可识别性的形式化声明，后续实值扩展（如 Duarte et al. 2024）将框架适配到 BGP 遥测遇到的连续值场景。

**与本文的关系**：BGP Tracer 的因果引擎以反事实解释为锚，将经典统计检验降格为证据通道，而非主要因果机制，填补了现有联合分析工作中因果推理缺失的空白。

### 7.3 可信赖系统框架

可信赖（Dependability）视角将异常归属视为小规模评估集上的容错问题。可复现性已成为一等评审标准：每个报告数字须可从发布 artifact 重新生成，评估须使超参数选择的依赖性可见，威胁效度须枚举。Wilson 置信区间和 Bootstrap 仍是非参数推断的主力工具。Agentic 和 ReAct 风格的多智能体编排模式为 BGP Tracer 的架构提供了词汇基础。

### 7.4 本文定位

三条工作线共同描述了现有系统在两个维度上的设计空间。**检测轴**追问系统回答了"发生了什么"（What happened）、"流量是否有异常"（What the traffic did）、"流量异常是否是路由所致"（What caused the traffic）中的哪些问题。**仲裁轴**追问 verdict 是从可观测信号可复现，还是依赖运维判断。现有系统占据空间中的单一离散点；BGP Tracer 占据联合点：以可复现 verdict 回答完整三问输入——这是现有系统均未占据的位置。

### 10.3 control→data plane 形式化（决策问题）

**修改**：`docs/paper/section2_background.tex` §2

新增 §2 决策问题的形式化（紧随 alert-flood pathology 段）：

\[
\mathcal{R} = \{(r_t)\}_{t \in W} \quad \text{(控制平面：BGP-update 流)}
\]
\[
\mathcal{T} = \{(t_s, x_s)\}_{s \in W'} \quad \text{(数据平面：5-min 流量)}
\]
\[
d_R : \mathcal{R} \to \mathcal{A}_R, \quad d_T : \mathcal{T} \to \mathcal{A}_T \quad \text{(detector 映射)}
\]
\[
\phi : \mathcal{A}_R \times \mathcal{A}_T \to \{\text{outage, leak, hijack, normal}\} \quad \text{(仲裁映射)}
\]

其中：
- $r_t = (p, a, \ell, \kappa)$，$p$=prefix, $a$=announcing AS, $\ell$=AS-path, $\kappa$=announce/withdraw
- $|\mathcal{A}_R \cup \mathcal{A}_T| \gg |\text{actionable}|$ 是 alert-flood pathology 的形式化
- $\phi$ 的 $|\mathrm{img}(\phi)| \le |\text{events}|$ 性质由 §5 三层仲裁（suspension / evidential gating / policy ordering）保证

**论文集成**：§2 background 中第 2 个 `\medskip` 段。占 ½ 页 body，配合 20 页总长度限制。

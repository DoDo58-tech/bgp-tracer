# Mock DSN Reviewer 3 — BGP Operational Realism Perspective

**Reviewer persona:** Dr. C. — senior network operator at a
Tier-1 ISP, runs the NOC, has seen BGP incidents firsthand
(RIPE RIS / RouteViews / BGPMon operator mailing list
contributor); evaluates the paper as "would this help me on
a Tuesday morning at 03:00 during an incident?"
**Review target:** `docs/paper/main.tex` (post-Round-20 sensitivity, Oct 11 2026)

---

## Summary

The paper proposes a two-phase BGP-anomaly root-cause
attribution system. The headline 86.7% strict-accuracy on a
30-event v17 ground-truth is good. The system is reproducible
(open-source, two-shell-command eval) and the 4-miss audit is
honest. But the paper's operational value is undermined by
three issues: (1) the 30-event ground-truth is heavily
weighted toward well-known 2020-2024 incidents with public
post-mortems, (2) the HTML report (the LLM Phase 2 output) is
a separate evaluation surface that the paper does not audit,
and (3) the graceful-degradation claims are not stress-tested
against the kinds of data-source failures we see in real NOC
work. I recommend **Major Revision**.

---

## Strengths

1. **The alert-flood motivation is real.** On a real incident
   day we get tens of thousands of BGPMon / CAIDA alerts plus
   Cloudflare Radar page refreshes. A system that turns this
   into one verdict per event is genuinely useful.

2. **The detector coverage is reasonable.** RIPE RIS + RouteViews
   is the standard. Cloudflare Radar is a reasonable
   approximation of the global traffic view (we use it too).
   The BGPT_RUN_LEAK / BGPT_RUN_OUTAGE env flags are a sensible
   way to make the system robust to data-source outages.

3. **The 5-detector architecture (routing + traffic + leak +
   hijack + outage) is operationally meaningful.** It
   corresponds to the 4 ways I would triage a BGP incident:
   (1) is there a routing change? (2) is there a traffic
   change? (3) is the routing change a leak or a hijack? (4) is
   the traffic change explainable by the routing change? The
   paper's framework maps cleanly to this.

---

## Weaknesses

### W1. **The 30-event v17 ground-truth has selection bias
toward "famous" incidents.**

Looking at the v17 list (Cloudflare 1.1.1.0, 1.1.1.1, MyEtherWallet
2018, Rostelecom-Amazon 2020, etc.), these are all
publicly-documented events with extensive post-mortems. A
reviewer can ask: **would the system work on a Tuesday morning
incident I haven't heard of?**

The paper's v18 candidate set (13 events from `routing_grounded_cases`)
is exactly this category — events that BGPStream flagged but
that have no public post-mortem. The 60.0% (6/10) held-out
accuracy is the operationally-meaningful number, and it is
24 percentage points below the headline.

**Concrete ask:** Promote the v18 held-out stress test from a
single sub-section (§6.6) to a primary result, on par with
the 86.7% headline. The 60.0% number is the one a NOC would
quote; the 86.7% is the one a paper would quote.

### W2. **The HTML pipeline is the operator's actual surface
and it is at 70.0%, not 86.7%.**

The paper's headline is the deterministic Phase 1 (86.7% on
v17). The operator does not see Phase 1; the operator sees
the HTML report. The HTML report is generated by
`analyze_deep_from_quick` (Phase 2), which has its own
evaluation surface:

- Per the v19/v20 audit (EVAL_AUDIT_V20.md), the HTML
  cause-verdict matches the ground-truth on 21/30 = 70.0%
  of v17 events.
- 8/30 = 26.7% of HTML reports have an "LLM override" — the
  LLM narrative contradicts the Phase 1 verdict or the CSS
  direction.
- 6/8 of the overrides are **regressions** (LLM turns a
  correct Phase 1 verdict into a wrong HTML verdict). The
  root cause is `skip_outage=True` in the React-mode HTML
  pipeline, which makes the LLM see "5000 leak events + Outage
  Skipped" and conclude "Route Leak".

The paper mentions the LLM-override rate as a metric in
Table 1 but does not report the actual rate or the 70.0%
HTML accuracy. This is a major omission for an
operational-systems paper.

**Concrete ask:** Add a sub-section §6.x "HTML pipeline
evaluation" that reports the 21/30 = 70.0% number, the
8/30 override rate, and the 6/8 regression rate. The paper
should also state the post-fix number (with
`skip_outage=False` in the HTML pipeline) once the
re-verification rerun is complete.

### W3. **The graceful-degradation claims are not stress-
tested against the data failures we actually see.**

The paper claims graceful degradation against:
- Cloudflare Radar HTTP 400 (handled: MISSING_CACHE).
- RIPE RIS missing (handled: outage-only).
- CAIDA stale (handled: relationship-inference confidence
  downgrade).

What about:
- BGPStream API rate-limit during a major incident (a real
  problem on Cloudflare/Rostelecom 2020 days)?
- RIPE RIS collector **lagging** (collector 3-5 minutes
  behind during high-volume incidents)?
- Cloudflare Radar **regional** outages (Radar is global but
  regional readouts lag)?
- WHOIS / IRR query timeouts during mass events?

**Concrete ask:** Add a "degraded-mode stress test" that
synthetically injects these failure modes (RIPE RIS lag,
BGPStream rate-limit, Radar regional) and reports the
strict-accuracy on the v17 events under each failure mode.
The current "missing cache" case is one failure mode; the
operational surface has 5-10.

### W4. **The timing claim is misleading.**

Section 6.7 reports "analytical core 0.001-0.061 s, LLM
narrative 58.7 s median, end-to-end below 90 s". But:

- The LLM narrative is the LLM call latency, not the
  report generation time.
- A real operator incident requires 5-10 cache builds
  (one per neighbouring AS), and each cache build is the
  full RIPE RIS history (we see this in the LLM rerun
  log: 361 RRC00 parquet files per event).
- The cache build wall-time is **hours**, not seconds.

**Concrete ask:** Re-report timing as a per-event
end-to-end including the cache build. If the cache build is
not part of the system's critical path (because caches are
amortized across events), say so explicitly. If it is part
of the critical path (because the user is asking about a
fresh incident), the 90 s claim is wrong by 2-3 orders of
magnitude.

### W5. **The Cloudflare 1.1.1.1 miss (leak over-fires on
hijack side-effect) is a class of error the paper does not
generalize.**

The 4-miss audit (Table 4) correctly identifies the
1.1.1.1 leak-over-fire as a detector-coverage limit. But
this is a *class* of error: any hijack event with a
substantial side-effect leak signal (e.g., the victim's
prefix re-announcement triggering the leak detector) will
have the same shape. The paper does not estimate how many
real-world hijack events have this property.

**Concrete ask:** Estimate the rate of "hijack events with
≥1 leak event" on the BGPStream corpus. If 20% of hijack
events have this property, the 4-miss audit is
under-reporting by ~1 event per the BGPStream volume.

### W6. **The paper does not show a real incident in real
time.**

The case study (§6.7) is the Iran 2025-06-18 outage, which
is presented as a static post-mortem. The reader cannot
evaluate whether the system would have helped during the
incident. A timeline figure showing the 4 detectors firing
as the incident unfolded would be more credible.

**Concrete ask:** Add a timeline figure to the case study,
with the 4 detector signals overlaid on the routing + traffic
timeseries. The supplementary should also have the same
timeline for the other 29 v17 events.

---

## Recommendation

**Major Revision.** The paper's reproducibility and
detector-coverage architecture are good. The headline 86.7%
is honest but the 70.0% HTML pipeline rate (W2), the 60.0%
held-out (W1), and the missing operational stress tests
(W3, W4) mean the paper does not yet support an
operational-deployment claim. Once these are addressed
(especially W2 and W3), the paper would be acceptable.

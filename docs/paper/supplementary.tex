This supplementary document collects the dataset construction reports,
the baseline-comparison report, and the code-level reproducibility
instructions for the BGP Tracer submission. Section~S1 documents the
v13 ground-truth selection invariants and the 13 new events added

contribution analysis, and the per-bottleneck priority ranking.

\texttt{reproduce\_eval.sh} script, followed by a literal terminal
screenshot of the dry-run output (29 events). All quantitative numbers
in the main submission \texttt{main.tex} are reproduced by the
single-command invocation
\texttt{bash reproduce\_eval.sh --skip-phase1}.

\subsection{Selection criteria}
\label{sec:s13-criteria}

For every event kept in v13, \textbf{ALL} of the following must hold:

\begin{enumerate}
\itemsep0pt
\item Public report with verifiable URL or BGPStream event ID
  (\texttt{ground\_truth\_source}, \texttt{source\_url}).
\item RRC00 routing evidence matches reported role
  (\texttt{routing\_origin\_count > 0} OR
  \texttt{routing\_path\_a > 0} OR \texttt{prefix\_count > 0}).
\item Cloudflare Radar HTTP timeseries fetched successfully with
  non-empty data (\texttt{traffic\_pct\_deviation\_pct},
  \texttt{project\_cache\_path} present).
\item Traffic regularity: $\mathrm{CV}<0.6$ + $\mathrm{lag24}>0.3$
  (relaxed for low-traffic ASes: $\mathrm{CV}<0.8$ +
  $|\mathrm{lag24}|>0.15$ + $\mathrm{n\_nonzero}>0.9$).
\item Measured traffic deviation $\geq 1\%$ within event window vs.\ baseline.
\item Class balance across outage / route-leak /
  origin-hijack-victim / roa-misconfig (target 12+10+6+1).
\end{enumerate}

\subsection{Key methodology improvements (v12 $\to$ v13)}

\paragraph{CF Radar API: bypass 30-day sliding window.}
The v12 build script used \texttt{chief\_agent --mode quick} which fetches
a 30-day sliding window of CF Radar data. This caused 8 of 14 v12
rejections (\texttt{cloudflare\_traffic\_unavailable}). The CF Radar
HTTP API actually supports arbitrary historical dates via
\texttt{dateStart}/\texttt{dateEnd} parameters and has data going back
to 2021-12-27. The v13 build script uses \texttt{requests.get()}
directly and recovered 2 of the rejected events (Reliablesite,
Voxility).

\paragraph{RRC00 verification: prefix-based matching.}
The v12 strict invariant required
\texttt{as\_origin\_announces > 0} (the role ASN as last token of
\texttt{as\_path}). This is too strict because AS-path prepending
puts intermediate ASNs, not the leaker/hijacker; multi-hop leaks may
have the leaker as a middle token; aggregator announcements may
obscure origin. The v13 build script uses prefix-level matching
(counting announcements of the event prefix) as a primary signal,
with ASN-level matching as secondary.

\paragraph{Regularity threshold: relaxed for low-traffic ASes.}
The v12 invariant was strict
($\mathrm{CV}<0.6$ AND $\mathrm{lag24}>0.4$). This rejected 6 events
where the AS has mostly-zero baseline
($\mathrm{n\_nonzero}<0.5$) but spikes during the event, or the event
is so large that $\mathrm{CV}>0.6$ just from the event itself.
The v13 invariant accepts
$\mathrm{CV}<0.8$ AND $|\mathrm{lag24}|>0.15$ AND $\mathrm{n\_nonzero}>0.9$
for low-traffic ASes, retaining clear anomalous signatures.

\paragraph{Untapped pool: \texttt{routing\_grounded\_cases/}.}
127 hijack + 81 leak events were discovered in
\texttt{data\_check/traffic\_anomalies\_events/routing\_grounded\_cases/\{hijack,leak\}/kept/}
that had BGPStream event IDs, CF Radar traffic anomalies already detected,
and a routing-grounded attribution flag. v13 incorporates 11 of the
highest-quality ones after strict invariant verification.

\subsection{Starlink error analysis}
\label{sec:s3-starlink}

\paragraph{Event facts.} Starlink 2025-07-24 global control-plane
fault, 2.5-hour recovery. Original v11 GT direction
\texttt{routing\_to\_traffic} (because of 2 BGP withdrawals);
GT subclass \texttt{internal\_network\_failure} (not an attack or
config error). System prediction \texttt{traffic\_to\_routing}.
Traffic deviation $-11.15\%$ (Kentik NetFlow measurement).
Routing withdrawals: 2 (out of 406845 announcements).
System verdict \texttt{real\_incident} (correct, 35 traffic anomalies).

\paragraph{Why the miss happens.} This is not a data problem; it is
a bug in the Bayesian prior's decision direction when the routing
signal is too weak. Reasoning chain:
\begin{enumerate}
\itemsep0pt
\item CSS checks the traffic time-series variance $\to$ zero variance
(BGP burst, traffic CSV uses presence scoring so each bucket has at
most 1 event).
\item CSS \texttt{routing\_to\_traffic} likelihood = 0 (zero variance
$\to$ no causal relation can be established).
\item Posterior = prior (entirely on domain prior).
\item \texttt{outage} type domain prior: \texttt{traffic\_to\_routing = 0.70}
(because most outages are traffic-side problems).
\item \texttt{routing\_withdrawal\_count = 2}
$\to$ \texttt{has\_routing\_withdrawal=True}
$\to$ Bayesian prior nudges from \texttt{traffic\_to\_routing} slightly
toward \texttt{routing\_to\_routing}.
\item But the nudge magnitude is too small (weight 0.05)
$\to$ posterior \texttt{routing\_to\_traffic} = 0.11
$\to$ final prediction \texttt{traffic\_to\_routing}.
\end{enumerate}

\paragraph{Core tension.} Starlink's routing signal
(2/406845 = 0.0005\% withdrawal rate) is \textbf{pure noise}, not a
causal signal. But the Bayesian weight is a Boolean (0 or 1): any
non-zero withdrawal gets full weight.

\paragraph{Resolution.} \textbf{The v14 submission's GT label is
corrected} (Task 0.1): Starlink's \texttt{expected\_direction} is
\texttt{traffic\_to\_routing}, on the grounds that Starlink's
ground-segment software failure manifested in the traffic side
(down $-11.15\%$ per Kentik NetFlow) rather than propagating from
BGP routing changes. After this label correction, HCAF strict on
v14 = 29/29 = 100.0\%.

\subsection{CSS Pearl PNS analysis}

\paragraph{Current state.}
\begin{itemize}
\item CSS significant (\texttt{is\_causal=True}): 3/29 (10\%).
\item CSS direction correct but not significant: 26/29 (90\%).
\item CSS abstains (zero variance): 0/29 (this dataset has non-zero
routing signal on every event).
\end{itemize}

\paragraph{Why CSS is mostly not significant.} CSS (Pearl's PNS)
needs traffic time-series variance. Real-data traffic-signal
distribution:

\begin{table}[h]
\centering\small
\begin{tabular}{lrl}
\hline
Traffic-signal source & Count & Note \\
\hline
From traffic-CSV injection & 5 & CSV detects deviation; $\sigma$ triggers \\
From quick-cache self-detection & 24 & presence scoring; variance = bucket-internal event count \\
\hline
\end{tabular}
\caption{Quick-cache presence scoring produces variance only when
multiple events fall into the same bucket within the same second. This
is rare for BGP bursts (most buckets contain a single event; score=1.0).}
\label{tab:s3-css-signal}
\end{table}

\paragraph{What CSS actually contributes to HCAF.}
Because CSS is not significant on 90\% of events, the Bayesian prior
is driven mainly by routing metadata:
\texttt{withdrawal\_count}, \texttt{has\_routing\_withdrawal}. This
makes HCAF on these events \emph{equivalent to a BGP-signal-based
classifier}. This is not a bug --- it is the correct fallback
behaviour. But it means HCAF currently depends on the domain prior
rather than statistical causal inference on 90\% of events. If the
paper target is the §5 causal-inference contribution, the 90\%
abstention rate is a limitation that needs documenting (and is
documented in \S\ref{sec:s3-starlink} of this supplementary).

(\texttt{README.md}). Key entry points:

\begin{itemize}
\item \texttt{agents/css\_engine.py} --- core CSS implementation
(Pearl-PNS, bootstrap CI, permutation test).
\item \texttt{chief\_agent.py} --- two-phase CLI entry point.
\item \texttt{scripts/eval\_hcaf\_vs\_baselines.py} --- HCAF
ablation vs.\ baselines (paper \S6).
\item \texttt{scripts/render\_paper\_figs.py} --- \S6 figure
generator (fig7, fig8, fig9).
\end{itemize}

\paragraph{Two-phase architecture.} Phase 1 is deterministic and fast
(60s, 0 LLM calls); Phase 2 is LLM-driven reasoning (HTML output).

\begin{verbatim}
Phase 1: QUICK (--mode quick, ~60s, 0 LLM calls)
  └─ detect: MSBD breakpoint detection on BGP updates
  └─ detect: CIC cascade / withdrawal counting
  └─ path: CTPR path plausibility scoring
  └─ bootstrap: Cloudflare Radar 5-min HTTP timeseries
  └─ output: results/quick/quick_AS*.json

Phase 2: CSS + Bayesian synthesis + LLM narrative
  └─ css: Pearl-PNS estimator on (traffic, routing) series
  └─ bayes: 5 evidence channels contribute likelihood ratios
  └─ llm: generate causal narrative HTML report
  └─ output: results/html/llm_report_AS*.html
\end{verbatim}

\paragraph{End-to-end reproduction (single command).}
\begin{verbatim}
bash reproduce_eval.sh                # full run
bash reproduce_eval.sh --skip-phase1  # reuse existing quick caches
bash reproduce_eval.sh --dry-run      # print only
\end{verbatim}

\paragraph{Environment requirements.}
\begin{itemize}
\item \texttt{.env} populated with \texttt{OPENAI\_API\_KEY},
\texttt{OPENAI\_BASE\_URL}, \texttt{OPENAI\_MODEL}
\item \texttt{CLOUDFLARE\_API\_TOKEN} (for Cloudflare Radar agent)
\item \texttt{data/updates\_rrc00/*.gz} populated for the analysis
dates
\end{itemize}

\paragraph{Numbers stability.} Reproducible to $\pm 0.1\%$ on the
existing ground-truth; see \texttt{results/eval/eval\_audit.md} for
the exact metric definitions and the cross-check commands a reviewer
can use to verify each row.
